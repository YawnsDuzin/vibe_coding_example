# 튜토리얼 8: AI와 디버깅 — 에러를 두려워하지 않기

> **이 단원에서 배우는 것**: 에러가 발생했을 때 당황하지 않고 원인을 찾는 방법을 배웁니다.
> Traceback 읽기, 프롬프팅 전략, 재현 가능한 버그 리포트 작성법을 익힙니다.

---

## 시작하기 전에

프로그래밍에서 에러는 **"실패"가 아니라 "단서"**입니다.
에러 메시지는 "어디에서 무엇이 잘못되었는지" 알려주는 **자동차 계기판의 경고등** 같은 것입니다.
경고등이 켜졌다고 당황하지 않고, 무슨 경고인지 확인하는 것이 중요합니다.

비개발자가 에러를 만났을 때 가장 흔한 반응은 "안 돼, 고쳐줘"입니다.
하지만 이렇게 하면 Claude Code도 무엇을 고쳐야 할지 모릅니다.
이 단원에서는 **에러를 읽고, 맥락을 정리하고, 정확하게 도움을 요청하는 방법**을 배웁니다.

---

## 실습 1: Traceback 읽기 — "에러 메시지 해부하기"

### 왜 이걸 배우나요?
Python의 에러 메시지(Traceback)는 처음 보면 **영어가 잔뜩 적힌 무서운 메시지**처럼 보입니다.
하지만 실제로는 아주 **친절한 안내문**입니다 — 어디에서, 무엇이, 왜 잘못되었는지 다 적혀 있습니다.

Traceback을 읽을 수 있으면:
- Claude Code에게 **정확한 정보**를 전달할 수 있습니다
- 에러의 원인이 코드에 있는지, 설정에 있는지, 데이터에 있는지 **구분**할 수 있습니다
- "AI가 고쳐준 것"이 실제로 맞는 수정인지 **검증**할 수 있습니다

### Claude Code에 입력해보세요

#### 1-1. Traceback 구조 배우기

```
아래 Python Traceback을 비개발자가 이해할 수 있게 해부해줘.
각 줄이 무엇을 의미하는지 한 줄씩 설명해줘.

Traceback (most recent call last):
  File "app/ui/login_form.py", line 45, in _on_login
    user = self.auth_service.login(username, password)
  File "app/services/auth_service.py", line 28, in login
    user = self.user_repo.get_by_username(username)
  File "app/repositories/user_repository.py", line 15, in get_by_username
    return session.query(User).filter(User.username == username).one()
sqlalchemy.exc.NoResultFound: No row was found when one was expected
```

### Traceback 읽는 법 핵심 정리

Traceback은 **아래에서 위로** 읽는 것이 핵심입니다:

```
1. 맨 아래 → "무엇이" 잘못되었나: NoResultFound (결과가 없는데 하나를 기대함)
2. 바로 위 → "어디에서" 잘못되었나: user_repository.py, 15번째 줄
3. 더 위   → "어떤 흐름으로" 여기까지 왔나: login_form → auth_service → user_repository
```

비유: Traceback은 **사고 경위서**입니다.
- 맨 아래 = "사고 내용" (무슨 일이 일어났는지)
- 중간 = "사고 경로" (어떤 길을 따라 여기까지 왔는지)
- 맨 위 = "출발점" (처음 시작한 곳)

### 자주 만나는 에러 유형

| 에러 이름 | 의미 | 비유 |
|-----------|------|------|
| `NameError` | 존재하지 않는 이름을 사용 | "김철수씨!" — 회사에 김철수가 없는 경우 |
| `TypeError` | 잘못된 타입 전달 | 숫자를 넣어야 하는데 글자를 넣은 경우 |
| `ImportError` | 모듈을 찾을 수 없음 | 도구 상자에 없는 도구를 꺼내려는 경우 |
| `AttributeError` | 객체에 없는 속성/메서드 호출 | 자동차에 날개가 없는데 "날아라" 명령 |
| `NoResultFound` | DB에서 결과를 못 찾음 | 서류함에서 없는 서류를 찾으려는 경우 |

### 검증 포인트 ✓
- [ ] Traceback을 "아래에서 위로" 읽어야 한다는 것을 이해하나요?
- [ ] 에러 메시지에서 "어디에서"와 "무엇이" 잘못되었는지 구분할 수 있나요?

## 실습 2: 프롬프팅 전략 — "Claude Code에게 잘 물어보는 법"

### 왜 이걸 배우나요?
같은 에러라도 **어떻게 질문하느냐**에 따라 Claude Code의 답변 품질이 달라집니다.
의사에게 "아파요"라고만 하면 진단이 어렵듯이,
Claude Code에게도 **맥락, 증상, 기대 동작**을 함께 전달해야 합니다.

### 나쁜 질문 vs 좋은 질문

| 나쁜 질문 | 좋은 질문 |
|-----------|-----------|
| "안 돼, 고쳐줘" | "로그인 버튼을 클릭하면 NoResultFound 에러가 나요. 존재하는 사용자로 로그인해도 같은 에러가 나요." |
| "에러 났어" | "app/services/auth_service.py의 login 메서드에서 이 Traceback이 발생해요: [Traceback 붙여넣기]" |
| "왜 안 되지?" | "DB에 사용자 데이터가 있는지 확인했고, username='admin'으로 조회하면 결과가 없어요. user_repository.py의 get_by_username에서 필터 조건이 잘못된 것 같아요." |

### Claude Code에 입력해보세요

#### 2-1. 좋은 디버깅 프롬프트 연습

```
내가 아래 에러를 만났다고 가정해줘:

상황: 앱을 실행하고 로그인 버튼을 클릭했더니 에러가 발생
에러 메시지: TypeError: login() missing 1 required positional argument: 'password'
위치: app/ui/login_form.py, line 42

이 에러의 원인이 무엇인지 분석해줘.
login_form.py에서 auth_service.login()을 호출하는 부분을 확인하고,
함수 시그니처와 호출 코드가 일치하는지 비교해줘.
```

#### 2-2. 맥락을 포함한 디버깅 프롬프트

```
디버깅할 때 Claude Code에게 제공하면 좋은 정보 템플릿을 만들어줘.
아래 항목을 포함해서:

1. 무엇을 하려고 했나 (기대 동작)
2. 실제로 무슨 일이 일어났나 (실제 동작)
3. 에러 메시지 (Traceback 전문)
4. 어떤 파일의 몇 번째 줄인지
5. 이미 시도한 것이 있다면

이 템플릿을 앞으로 에러가 나올 때마다 사용할 수 있게 정리해줘.
```

### 디버깅 프롬프트 3원칙

1. **맥락을 제공하세요** — "어떤 상황에서" 에러가 났는지
2. **증거를 붙이세요** — Traceback, 에러 메시지를 그대로 복사
3. **범위를 좁혀주세요** — "이 파일의 이 함수가 의심돼요"

### 검증 포인트 ✓
- [ ] "안 돼, 고쳐줘" 대신 맥락을 포함한 질문을 할 수 있나요?
- [ ] 에러 발생 시 Claude Code에게 전달해야 할 정보 3가지를 알고 있나요?

## 실습 3: 재현 가능한 버그 리포트 작성하기

### 왜 이걸 배우나요?
버그를 고치려면 먼저 **"어떻게 하면 이 버그가 다시 나타나는지"**를 알아야 합니다.
이것을 **재현 조건(reproduction steps)**이라고 합니다.

의사에게 "어제 저녁 먹고 나서, 뛰었더니, 오른쪽 무릎이 아팠어요"라고 말하는 것처럼,
버그도 **"무엇을 하면 어떻게 되는지"**를 정확히 적어야 합니다.

### Claude Code에 입력해보세요

#### 3-1. 버그 리포트 작성 연습

```
다음 상황을 재현 가능한 버그 리포트로 작성하는 방법을 보여줘:

상황: 할 일 목록에서 "완료" 체크박스를 클릭하면 앱이 멈춤

버그 리포트에 포함해야 할 항목:
1. 제목 (한 줄 요약)
2. 환경 (OS, Python 버전, 앱 버전)
3. 재현 절차 (1단계, 2단계, 3단계...)
4. 기대 동작 (어떻게 되어야 하는지)
5. 실제 동작 (실제로 무슨 일이 일어나는지)
6. 스크린샷 또는 에러 로그
7. 추가 정보 (항상 발생하는지, 특정 조건에서만 발생하는지)
```

#### 3-2. 로그 파일 활용

```
app/core/logger.py가 어떻게 설정되어 있는지 확인하고,
에러가 발생했을 때 로그 파일(logs/ 디렉토리)에서
관련 로그를 찾는 방법을 알려줘.

로그 레벨(DEBUG, INFO, WARNING, ERROR)의 차이도 설명해줘.
```

### 버그 리포트 예시

```markdown
## 버그: 할 일 완료 체크 시 앱 프리즈

### 환경
- OS: Windows 11
- Python: 3.11.5
- DB: SQLite

### 재현 절차
1. 앱 실행 후 로그인
2. 할 일 목록 화면으로 이동
3. 할 일 항목의 "완료" 체크박스 클릭
4. → 앱이 약 5초간 응답 없음

### 기대 동작
체크박스를 클릭하면 즉시 완료 상태로 변경되어야 함

### 실제 동작
체크박스 클릭 후 앱이 5초간 프리즈, 이후 정상 동작

### 로그
[ERROR] 2026-04-16 14:30:22 - DB lock timeout in task_repository.py:42
```

### 검증 포인트 ✓
- [ ] "재현 절차"의 의미를 이해하나요? (답: 버그를 다시 만들어내는 단계별 방법)
- [ ] 로그 파일에서 ERROR 수준의 메시지를 찾을 수 있나요?
- [ ] "항상 발생" vs "가끔 발생"의 차이가 디버깅에 왜 중요한지 이해하나요?

## 실습 4: GUI 특유의 디버깅

### 왜 이걸 배우나요?
PyQt5 같은 GUI 앱은 일반 Python 스크립트와 다른 특유의 문제가 발생합니다.
특히 **이벤트 루프**, **DB 락(Lock)**, **위젯 생명주기** 관련 문제가 자주 나타납니다.

이런 문제들은 에러 메시지가 없거나 모호해서 비개발자가 특히 당황하기 쉽습니다.
"에러도 안 나는데 왜 안 되지?" 하는 상황이 바로 이것입니다.

### Claude Code에 입력해보세요

#### 4-1. 흔한 GUI 버그 패턴 학습

```
PyQt5 앱에서 비개발자가 자주 만나는 GUI 관련 버그 패턴 3가지를 설명해줘.
각 패턴에 대해:
1. 어떤 증상이 나타나는지
2. 원인이 무엇인지
3. 어떻게 해결하는지
4. Claude Code에게 어떻게 도움을 요청하면 좋은지

특히 이벤트 루프 블로킹, DB 락, 시그널/슬롯 연결 오류를 다뤄줘.
```

#### 4-2. 디버깅 Skill 만들기

```
다음 기능을 하는 커스텀 Skill을 만들어줘:

Skill 이름: /debug
용도: 에러 발생 시 원인 분석 → 수정 제안 → 테스트까지 단계별 가이드
입력: 에러 메시지 또는 증상 설명
출력:
  1. 에러 원인 분석
  2. 관련 코드 위치 식별
  3. 수정 코드 제안
  4. 수정 후 확인 방법

.claude/skills/debug/SKILL.md 파일로 만들어줘.
```

### GUI 디버깅 핵심 패턴

| 증상 | 가능한 원인 | Claude Code에게 물어볼 프롬프트 |
|------|-------------|-------------------------------|
| 앱이 멈춤(프리즈) | 이벤트 루프 블로킹 — 오래 걸리는 작업이 메인 스레드에서 실행됨 | "이 함수가 이벤트 루프를 블로킹하는지 확인해줘" |
| 버튼 클릭해도 반응 없음 | 시그널/슬롯 연결 누락 | "이 버튼의 clicked 시그널이 어디에 connect되어 있는지 찾아줘" |
| DB 관련 에러 | DB 락 — 다른 작업이 DB를 사용 중 | "세션이 제대로 닫히고 있는지 확인해줘" |
| 화면이 갱신 안 됨 | UI 업데이트 누락 | "데이터 변경 후 UI를 갱신하는 코드가 있는지 확인해줘" |

### 검증 포인트 ✓
- [ ] "이벤트 루프 블로킹"이 무엇인지 비유로 설명할 수 있나요?
  (답: 식당 카운터에서 주문 받는 사람이 직접 요리하러 가서 다른 손님 주문을 못 받는 상황)
- [ ] 버튼이 반응하지 않을 때 첫 번째로 확인할 것이 무엇인지 아나요?
  (답: 시그널/슬롯 연결 — `clicked.connect(함수)`)

## 이 단원을 마치며

축하합니다! 이제 여러분은:
- **Traceback**을 아래에서 위로 읽을 수 있습니다
- 에러 발생 시 **맥락, 증거, 범위**를 포함한 질문을 할 수 있습니다
- **재현 가능한 버그 리포트**를 작성할 수 있습니다
- GUI 앱 특유의 **디버깅 패턴**을 이해합니다

에러는 적이 아니라 **길을 알려주는 이정표**입니다.
에러 메시지가 무섭게 느껴지더라도, 핵심은 항상 맨 아래 한 줄에 있습니다.
그 한 줄만 읽을 수 있으면, Claude Code와 함께 어떤 에러든 해결할 수 있습니다.

다음 단원에서는 **AI가 만든 코드를 검증하는 방법**을 배웁니다.
Claude Code가 항상 옳은 것은 아닙니다 — 검증하는 습관이 바이브코딩의 핵심입니다.
