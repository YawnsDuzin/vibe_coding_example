# 튜토리얼 6: 요구사항 → 설계

> **이 단원에서 배우는 것**: 머릿속의 아이디어를 체계적인 문서(PRD, ERD, 아키텍처)로 바꾸는 방법을 배웁니다.
> "무엇을 왜 만드는지"를 명확하게 정의한 뒤, Claude Code와 함께 설계 문서를 만들고 작업을 분해합니다.

---

## 시작하기 전에

지금까지 우리는 보일러플레이트의 코드를 **읽고 이해하는** 데 집중했습니다.
이번 단원부터는 관점이 바뀝니다 — **"내가 만들고 싶은 것"을 정의하고 설계하는 사람**이 되는 것입니다.

비유하자면, 지금까지는 다른 사람이 지은 건물의 **안내도를 읽는 법**을 배웠다면,
이제부터는 **내가 짓고 싶은 건물의 설계도를 그리는 법**을 배웁니다.
설계도를 잘 그려야 시공사(Claude Code)가 제대로 지을 수 있습니다.

---

## 실습 1: PRD 작성하기 — "무엇을 왜 만드는가"

### 왜 이걸 배우나요?
PRD(Product Requirements Document, 제품 요구사항 문서)는 **"무엇을 왜 만드는지"를 적은 기획서**입니다.
건축에서 건축주가 "3층 건물, 1층은 카페, 2~3층은 사무실"이라고 적는 것과 같습니다.

PRD가 없으면 Claude Code에게 "그냥 앱 만들어줘"라고 하게 되고,
Claude Code는 여러분이 원하는 것과 **전혀 다른 것**을 만들어 줄 수 있습니다.

### Claude Code에 입력해보세요

#### 1-1. PRD 초안 생성

```
나는 "개인 독서 기록 앱"을 만들고 싶어.

요구사항:
- 읽은 책을 등록할 수 있다 (제목, 저자, 읽기 시작일, 완독일)
- 책마다 별점(1~5)과 한줄평을 남길 수 있다
- 읽고 있는 책 / 다 읽은 책 / 읽고 싶은 책을 구분할 수 있다
- 월별로 몇 권 읽었는지 통계를 볼 수 있다

이 요구사항을 PRD 형식으로 정리해줘.
목적, 대상 사용자, 핵심 기능 목록, 비기능 요구사항(성능, 보안 등)을 포함해줘.
```

#### 1-2. PRD 검토

```
방금 작성한 PRD에서 빠진 것이 없는지 확인해줘.
특히:
- 사용자 인증이 필요한지 (로그인)
- 데이터 백업은 어떻게 할지
- 화면은 몇 개가 필요한지
이 세 가지 관점에서 보완할 점을 알려줘.
```

### 핵심 포인트

PRD에 담아야 할 최소 항목:

| 항목 | 설명 | 예시 |
|------|------|------|
| 목적 | 왜 만드는가 | "독서 습관을 기록하고 동기부여" |
| 대상 사용자 | 누가 쓰는가 | "혼자 사용하는 개인 사용자" |
| 핵심 기능 | 무엇을 하는가 | "책 CRUD, 별점, 통계" |
| 비기능 요구사항 | 어떻게 동작해야 하는가 | "오프라인에서도 작동 (SQLite)" |

### 검증 포인트 ✓
- [ ] PRD를 읽고 "이 앱이 뭘 하는 앱인지" 한 문장으로 설명할 수 있나요?
- [ ] 핵심 기능과 "나중에 해도 되는 기능"을 구분할 수 있나요?

## 실습 2: ERD 설계하기 — "데이터를 어떻게 정리할까"

### 왜 이걸 배우나요?
ERD(Entity Relationship Diagram)는 **데이터의 설계도**입니다.
3단원에서 배운 테이블-컬럼-관계를 시각적으로 표현한 것입니다.

건축 설계에서 "방이 몇 개고, 각 방의 크기와 연결 통로는 어떻게 되는지" 그리는 것과 같습니다.
ERD 없이 코드를 짜기 시작하면, 나중에 "이 데이터를 어디에 저장하지?"라는 문제에 반드시 부딪힙니다.

### Claude Code에 입력해보세요

#### 2-1. ERD 생성

```
위의 독서 기록 앱 PRD를 기반으로 ERD를 설계해줘.
Mermaid 다이어그램으로 보여주고, 각 테이블의 컬럼과 관계를 설명해줘.

보일러플레이트의 User 모델(app/models/user.py)과 연동되도록 설계해줘.
사용자 한 명이 여러 권의 책을 등록할 수 있어야 해.
```

#### 2-2. ERD 검증

```
이 ERD에서 확인해야 할 것들:
1. 한 사용자가 같은 책을 두 번 등록하면 어떻게 되나?
2. 책의 "상태"(읽는 중/완독/읽고 싶음)를 컬럼으로 관리하는 것과 별도 테이블로 관리하는 것의 장단점은?
3. 월별 통계를 위해 어떤 쿼리가 필요한지 미리 확인해줘.
```

### 핵심 포인트

ERD에서 가장 중요한 것은 **관계(Relationship)**입니다:

```
User (1) ──── (N) Book
 └── 한 사용자가 여러 권의 책을 등록할 수 있다

Book (1) ──── (1) Review
 └── 한 권의 책에 하나의 리뷰를 남길 수 있다
```

### 검증 포인트 ✓
- [ ] 각 테이블이 PRD의 어떤 기능에 대응하는지 설명할 수 있나요?
- [ ] 1:N 관계가 왜 필요한지 (User와 Book) 설명할 수 있나요?
- [ ] 보일러플레이트의 기존 User 모델과 어떻게 연결되는지 이해하나요?

## 실습 3: 아키텍처 설계하기 — "누가 어디에서 무슨 일을 하나"

### 왜 이걸 배우나요?
아키텍처는 **코드의 역할 분담표**입니다.
회사에서 팀이 나뉘어 있듯이 (영업팀, 재무팀, 인사팀), 코드도 역할별로 나누는 것이 중요합니다.

보일러플레이트에서 계속 봐왔던 `UI → Service → Repository → Model` 구조를
이제 **내 앱에 맞게 설계**하는 연습을 합니다.

### Claude Code에 입력해보세요

#### 3-1. 계층별 역할 설계

```
독서 기록 앱의 아키텍처를 설계해줘.
보일러플레이트의 계층 구조(UI → Service → Repository → Model)를 따르되,
각 계층에 어떤 파일과 클래스가 필요한지 구체적으로 보여줘.

예시:
- Model 계층: 어떤 모델이 필요한가?
- Repository 계층: 어떤 데이터 조회/저장 메서드가 필요한가?
- Service 계층: 어떤 비즈니스 로직이 필요한가?
- UI 계층: 어떤 화면이 필요한가?
```

#### 3-2. 데이터 흐름 확인

```
"사용자가 새 책을 등록하는" 시나리오에서 데이터가
UI → Service → Repository → Model → DB 순서로
어떻게 흘러가는지 단계별로 보여줘.
보일러플레이트의 회원가입 흐름(auth_service.py → user_repository.py → user.py)과
비교해서 설명해줘.
```

### 핵심 포인트

```
사용자가 "책 추가" 버튼 클릭
    ↓
UI (book_form.py)           → 입력값 수집, 검증 (제목이 빈칸인지 등)
    ↓
Service (book_service.py)   → 비즈니스 판단 (중복 등록인지 등)
    ↓
Repository (book_repository.py) → DB에 저장
    ↓
Model (book.py)             → 테이블 구조 정의
    ↓
데이터베이스 (SQLite)
```

왜 이렇게 나누나요? 비유로 설명하면:
- **UI**는 **접수 창구**입니다 — 고객 응대만 합니다
- **Service**는 **심사 담당자**입니다 — 규칙에 맞는지 판단합니다
- **Repository**는 **서류 보관함 담당자**입니다 — 넣고 빼기만 합니다
- **Model**은 **서류 양식**입니다 — 어떤 칸에 뭘 적는지 정해놓은 것입니다

### 검증 포인트 ✓
- [ ] 왜 UI에서 바로 DB에 접근하면 안 되는지 설명할 수 있나요?
- [ ] 새로운 기능(예: "독서 목표 설정")을 추가하려면 어떤 계층에 무엇을 만들어야 하는지 판단할 수 있나요?

## 실습 4: To-do 분해하기 — "코끼리를 한 입씩 먹는 법"

### 왜 이걸 배우나요?
큰 프로젝트를 한 번에 만들려고 하면 **어디서부터 시작해야 할지 막막**합니다.
"코끼리를 먹는 법은? 한 입씩!"이라는 비유처럼,
큰 기능을 **작은 작업 단위로 쪼개는 것**이 핵심입니다.

각 작업 단위는 "한 번에 커밋할 수 있는 크기"가 이상적입니다.
1단원에서 배운 Git 커밋이 여기서 연결됩니다.

### Claude Code에 입력해보세요

#### 4-1. 기능별 To-do 분해

```
독서 기록 앱을 만드는 작업을 To-do 리스트로 분해해줘.
다음 기준으로 나눠줘:

1. 계층별로 나누기 (Model → Repository → Service → UI 순서)
2. 각 To-do는 1~2시간 안에 완료 가능한 크기
3. 각 To-do의 완료 기준(Done의 정의)을 명시
4. 의존 관계 표시 (어떤 작업이 먼저 끝나야 다음을 할 수 있는지)

마크다운 체크리스트 형태로 만들어줘.
```

#### 4-2. 우선순위 정하기

```
위의 To-do 리스트에서 MVP(최소 기능 제품)에 필요한 것만 골라줘.
"반드시 있어야 하는 것"과 "있으면 좋은 것"을 구분해줘.

MVP 기준: 책을 등록하고, 목록을 보고, 상태를 바꿀 수 있으면 MVP.
별점, 통계, 검색은 MVP 이후로 미루자.
```

### 핵심 포인트

To-do 분해의 좋은 예와 나쁜 예:

| 나쁜 To-do | 좋은 To-do |
|------------|------------|
| "책 기능 만들기" | "Book 모델 생성 (title, author, status 컬럼)" |
| "화면 만들기" | "책 등록 폼 UI 작성 (제목, 저자 입력칸 + 저장 버튼)" |
| "DB 연결하기" | "BookRepository에 create(), get_all() 메서드 추가" |

### 검증 포인트 ✓
- [ ] 각 To-do를 읽고 "무엇을 하면 되는지" 바로 이해할 수 있나요?
- [ ] MVP와 MVP 이후 기능을 구분할 수 있나요?
- [ ] To-do의 순서가 왜 Model → Repository → Service → UI인지 설명할 수 있나요?
  (답: 아래 계층부터 만들어야 위 계층에서 사용할 수 있으니까)

## 커스텀 Skill: `/plan-feature`

이 단원에서 반복되는 작업 패턴(요구사항 → PRD → ERD → 아키텍처 → To-do)을
커스텀 Skill로 만들 수 있습니다.

### Claude Code에 입력해보세요

```
이 작업 패턴을 커스텀 Skill로 만들어줘:

Skill 이름: /plan-feature
용도: 기능 설명을 입력하면 PRD + ERD + 계층별 To-do를 한 번에 생성
입력: 기능에 대한 자연어 설명
출력: PRD 문서, Mermaid ERD, 계층별 To-do 체크리스트

.claude/skills/plan-feature/SKILL.md 파일로 만들어줘.
```

## 이 단원을 마치며

축하합니다! 이제 여러분은:
- 머릿속 아이디어를 **PRD 문서**로 정리할 수 있습니다
- 데이터 구조를 **ERD**로 시각화할 수 있습니다
- 보일러플레이트의 **계층 구조에 맞게 아키텍처를 설계**할 수 있습니다
- 큰 프로젝트를 **작은 To-do로 분해**할 수 있습니다

기억하세요: Claude Code가 PRD, ERD, To-do의 **초안을 만들어 주지만**,
그것을 **검토하고 수정하고 확정하는 것**은 여러분의 몫입니다.
설계는 "정답"이 아니라 "선택"입니다 — 여러분이 **왜 이렇게 설계했는지** 설명할 수 있으면 됩니다.

다음 단원에서는 **Claude Code의 환경을 최적화**하는 방법을 배웁니다.
CLAUDE.md, 커스텀 Skills, 프롬프트 로깅으로 Claude Code를 **나만의 개발 파트너**로 만듭니다.
